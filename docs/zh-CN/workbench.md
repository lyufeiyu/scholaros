# 项目工作台与交付

[English](../workbench.md) | **简体中文**

ScholarOS 0.2 将用户工作台与七阶段执行游标分开：工作台包括配置、材料、贡献、证据、稿件、图件、审阅和交付八区；底层仍使用原有可恢复状态机，旧项目保持兼容。

## 配置任务

可选择六类工作：由材料形成论文、重写已有稿件、科研诚信与证据核查、独立审阅、按意见返修、适配新目标。配置还记录使用场景和目标名称、输出语言、研究分析边界、作者表达、学习集篇数、参考文献目标、机制图策略、交付范围和格式。

配置保存在项目 JSON 中，旧项目无需数据库迁移即可获得保守默认值。字段变化只从最早受影响阶段开始失效，旧版生成内容会先进入历史快照。只改变交付格式时会立即撤销旧导出，避免把过期稿包继续展示为当前版本。

“只使用已有材料与结果”会完全跳过第三方论文检索；如果项目中没有任何本地资料或结果，工作流会停止并提示补充材料，不会静默改回联网模式。

命令行示例：

```bash
scholaros run "你的研究问题" \
  --workflow transfer --scene conference --target-name DemoConf \
  --language zh --research-mode materials_only \
  --same-field-papers 5 --target-venue-papers 5 \
  --reference-count 30 --format md --format tex
```

## 做有边界的选择

范围界定后，系统给出三个带取舍说明的贡献方向；选择后仍留在同一项目，并在必要时使证据及其下游结果失效。图件故事板为每张候选图记录职责、证据状态、媒体占位、保留/修改/省略选择和意见。缺少图片或视频素材不会阻塞规划；没有结果资料时，结果图明确保持“等待真实结果”。

## 在同一项目返修

反馈可针对稿件、图件或整项工作。返修前自动保存当前版本，后续每轮都以前一轮完成稿为起点。图件反馈会作为修改请求写回故事板；未配置模型时，尚未实际完成的稿件修改会保留为 `manual_required`，不会假装已经改写。受影响制品只有在对应阶段实际运行后才会替换。

## 准备交付

可在 Web 交付区、API 或命令行执行：

```bash
scholaros delivery PROJECT_ID
```

交付阶段可从已审阅的 Markdown 生成 `paper.docx` 和 `paper.tex`，再写出 `delivery-manifest.json` 与 `delivery-package.zip`。清单记录请求、可用和缺失格式，质量与反馈阻塞项，文件大小和 SHA-256，共享边界，以及“本地交付不等于投稿或发布”。“仅稿件”和“投稿材料包”只包含请求的稿件格式；“完整本地稿包”还包含证据、设计、图件故事板和内部审阅记录，可能带有上传材料摘录，因此对外分享前必须人工检查。ZIP 不包含原始上传资料、密钥、数据库、历史版本和本机路径。只有真实存在 `paper.pdf` 时才会标记 PDF 可用，系统不会拿其他文件冒充 PDF。

DOCX 和 TeX 是可编辑基础稿，不是已经套好目标期刊版式的终稿。研究者仍需补充最终媒体，回到原文核验证据，应用目标场景的最新模板，确认作者、伦理、基金等元数据，并亲自决定是否投稿。
